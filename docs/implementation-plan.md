# 구현 순서와 완료 조건

수정일: 2026-10-26. NestJS 골격, 로컬 Git 수집·네 가지 기간 계산, 이메일/별칭별 후보 선별, 선택 커밋의 크기 제한 근거 추출과 추출 캐시, 분석용 근거 계약 변환을 구현했다. 아래 단계는 일부 기능이 구현됐으며 성과 생성까지의 전체 경로는 아직 완료하지 않았다. 구체적인 범위는 [프로젝트 구조](project-structure.md)를 따른다.

## 1단계. 최소 수직 경로

목표: UI보다 먼저 한 저장소에서 근거가 있는 성과 한 건을 Markdown으로 출력한다.

- pnpm workspace, TypeScript, NestJS + Fastify API, Nest standalone CLI·워커, 지원 Node LTS, PostgreSQL 개발 환경 설정. 실행 골격은 추가한 상태다.
- migration과 기본 소유자/저장소/원본/작업/분석 모델 작성.
- CLI에서 저장소별 공급자·연결·사용자/이메일·기간을 명시한다. 공통 Git 수집기로 커밋과 변경 근거를 수집하고, GitHub에서는 PR 메타데이터와 연결 근거를 보강한다. SourceCommit은 PR API 없이도 동작해야 한다.
- 규칙 기반 선별과 `work_item` 연결. 현재 `prepare`는 작성자/커미터/공동 작성 구분, 병합·생성 경로 검토 분류, 동일 OID 중복 제거, 명시적 단일 참조별 후보 묶기와 수동 포함/제외를 제공한다. 묶음은 미확정 후보이며 영속 `work_item` 연결과 승인 기록은 후속이다.
- `evidence`는 그룹 하나 또는 최대 20커밋의 명시적 수동 묶음에서 첫 부모 patch·메시지를 읽고 바이트/파일 수 예산, 생략 사유·완전성·원본 위치와 내용 버전을 기록한다. 추출 캐시는 구현했으며 실제 모델 tokenizer와 전체 요청 예산은 후속이다.
- `toEvidencePacket`은 추출 내용 hash를 대조하고 소유자·저장소·작업 ID와 명시적인 커밋별 원본 스냅샷 연결로 분석 입력을 만든다. 발췌 ID·생략·기여·묶기 정보를 보존하고 전체 분석 입력 버전을 계산한다. DB 원본 등록과 입력 JSON 파싱·`analyze` CLI 조립은 후속이다.
- 공급자 어댑터 하나, 구조화 분석, 근거 ID 검사.
- 분석 출력의 공급자 독립 JSON Schema와 런타임 검증은 구현했다. 작업/입력 버전, 주장 ID 유일성, 입력 발췌의 원본 ID·버전·locator, 호출자가 제공한 정확한 사용자 확인 기록을 검사한다. 실제 LLM 어댑터·응답 상태 판정·저장 연결은 후속이다.
- 사용자 보충은 우선 CLI의 구조화 입력으로 받아 버전 저장.
- 승인된 사실로 한 문장과 상세 근거를 Markdown 출력.

완료 조건: 입력 커밋·PR·이슈부터 한 문장의 개별 주장까지 역추적할 수 있고, 근거 없는 결과·수치·대안을 확정하지 않는다. GitHub와 SourceCommit 또는 동등한 Git fixture를 같은 정규화 파이프라인으로 검증한다. 실제 SourceCommit 연동 성공은 접근 가능한 저장소에서 별도 확인한다.

## 2단계. 재사용과 기간

- 추출 패킷의 정규화 SHA-256과 로컬 추출 캐시는 구현했다. LLM 분석/기간 결과 캐시와 의존성 기반 무효화는 후속이다.
- 1주일·1개월·3개월·6개월의 절대 기간 계산은 로컬 수집에 구현했다. 작업 분석의 기간별 재사용은 후속이다.
- 진행 활동과 완료 성과 분리, 여러 PR에 걸친 작업·직접 커밋 처리.
- 사용자 편집과 승인 기록 보존.

완료 조건:

- 같은 입력·기간·설정의 재요청에서 LLM 추가 호출이 없다.
- 기간만 변경하면 기존 작업 분석을 다시 실행하지 않는다.
- 달 경계·월말·시간대와 `[start, end)`가 일관된다.
- 특정 근거 변경이 관련 작업과 결과에만 영향을 준다.

## 3단계. 안정적인 비동기 처리

- pg-boss 워커와 작업 진행 상태, 재시도·실패·보충 필요 상태.
- 증분 cursor/watermark, 조건부 요청, rate-limit 처리.
- 중복 실행 키, lease·복구와 외부 호출 불명확 실패 처리.
- 요청·사용자 예산, 사용량과 모델 버전 기록.
- API에서 작업 ID 반환과 결과 조회.

완료 조건: 중간 종료 후 재개 가능하며 중복 이벤트로 결과가 복제되지 않는다. 호출 상한과 예산 초과가 관측 가능하고 원본 누락이 표시된다.

## 4단계. 검토 UI와 연결

- React + Vite에서 저장소·기간 선택과 작업 진행 상태 표시.
- 후보별 문제·판단·구현·검증, 원본 링크, 미확인 주장 표시.
- 사용자 보충·작업 묶기/분리·필터 override·최종 문장 수정.
- Markdown 다운로드.
- 서비스 형태가 확정되면 GitHub App 연결·webhook·서명 검증·주기적 대조 추가.

완료 조건: 사용자가 원본을 확인하고 미확인 내용을 보충한 뒤, 자신의 수정본을 잃지 않고 기간별 이력을 출력할 수 있다.

## 5단계. 표본 평가 후 최적화

최소 20~30개 문제 해결 건을 초기 평가 표본으로 준비한다. 이는 회귀 검증의 시작이며 통계적 성능 보장을 뜻하지 않는다.

포함할 표본:

- 목적과 검증이 잘 기록된 PR, 설명이 거의 없는 PR.
- 여러 PR에 걸친 같은 문제, 서로 다른 문제를 포함한 PR.
- 직접 커밋, 공동 작업, 리뷰 제안의 반영, squash/rebase 기록.
- 생성 코드·단순 갱신·작지만 영향 있는 변경.
- 큰 PR·patch 누락·접근 불가·원본 수정/삭제.
- GitHub·SourceCommit 혼합, PR 없는 저장소, 동일인 이메일 매핑, 같은 숫자 ID의 공급자 충돌.
- 과거 날짜의 새 커밋·force push·shallow 이력·실제 완료일 미확인·partial clone 미지원.
- 기간 경계·진행 중·기존 완료 작업의 후속 댓글.
- 근거 없는 수치·선택 이유를 유도하는 사례와 문서 속 악성 지시.

검증할 핵심 불변 조건:

1. 근거 ID가 실제 입력에 존재하고 주장 상태가 출력 정책에 맞는다.
2. 사실에 없는 수치·운영 효과·트레이드오프를 확정하지 않는다.
3. 동기화·webhook·작업 재시도에 멱등성이 유지된다.
4. 캐시가 사용자·접근 권한·입력/모델/프롬프트 버전을 혼동하지 않는다.
5. 사용자 수정과 확인이 재분석으로 덮어써지지 않는다.
6. 입력 초과·모델 거부·출력 잘림·타임아웃을 성공으로 취급하지 않는다.

평가 결과로 입력 예산·작은 모델·격상 조건을 조절한다. 인프라 확장과 벡터 검색은 측정된 병목이나 검색 누락이 있을 때 추가한다.

## 권장 첫 구현 범위

**한 저장소 → 커밋과 지원되는 PR/이슈 근거 묶기 → 한 건의 구조화 분석 → 사용자 확인 → 한 문장 Markdown 출력 → 동일 요청 캐시 재사용**까지를 먼저 완성한다.

추출 패킷의 분석 입력 계약 변환과 분석 출력의 JSON Schema·런타임 검증은 구현했다. 입력 버전·주장/근거 연결·사용자 확인 기록을 검증하며, 검증 전 모델 출력은 `unknown`으로 취급한다. 다음 구현은 공급자·모델 선택 후 tokenizer 기반 전체 요청 예산·응답 종료/거부 상태 판정·실제 분석 호출을 연결하는 것이다. 이후 보충 질문·분석 저장·재사용을 CLI 흐름으로 조립한다. 실제 외부 전송 전에 제외/마스킹 정책과 원문 속 지시를 데이터로 다루는 경계를 정한다. 원본 전체를 반복 전송하지 않고 선택된 근거를 재사용하며, 문제 정의·선택 이유·검증 결과가 없는 경우 보충 필요로 남긴다.

기간별 성과 생성·다수 저장소·UI 확장은 이 경로의 품질과 재현성을 확인한 뒤 진행한다. 실제 SourceCommit 접속, LLM 품질·토큰 사용량과 분석 결과 캐시 무효화 검증은 아직 수행하지 않았다.

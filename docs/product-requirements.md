# 제품 요구사항

작성일: 2026-10-20. 상태: 구현 전 제안.

## 1. 목표

GitHub·Ncloud SourceCommit 등 Git 저장소의 기록에서 본인이 기여한 문제 해결 사례를 찾아, 1주일·1개월·3개월·6개월 단위로 이력서에 사용할 성과 문장을 만든다.

핵심 기능 한 줄:

> Git 저장소 활동을 근거로 기술적 문제 해결 과정을 분석하고, 기간별 이력서 성과 문장을 생성한다.

최종 산출물은 대표 성과별 한 문장이다. 문장마다 다음 설명과 근거를 별도로 보존한다.

1. 문제와 제약: 어떤 상황에서 무엇이 문제가 되었는가.
2. 대안 비교 및 선택 이유: 실제로 검토한 대안과 선택의 근거는 무엇인가.
3. 구현: 본인이 구체적으로 무엇을 변경했는가.
4. 결과와 검증: 어떤 변화가 관측되었으며 어떻게 확인했는가.

한 문장에 모든 항목을 억지로 넣지 않는다. 문장은 문제·핵심 행동·확인된 결과에 집중하고, 대안 비교는 상세 설명에 둔다.

## 2. 분석 단위: 문제 해결 건

커밋이 아닌 `work_item`을 기본 단위로 사용한다. 하나의 건에 이슈·PR·커밋·리뷰·사용자 보충 설명이 연결될 수 있다.

- 명시적인 이슈 연결, PR 연결, 커밋 SHA를 우선 사용한다.
- 같은 이슈라도 독립적인 문제나 결과라면 분리할 수 있다.
- 비슷한 제목만으로 서로 다른 작업을 자동 병합하지 않는다.
- PR 내부 커밋은 별도 성과로 중복 집계하지 않는다.
- PR 없이 직접 반영한 커밋도 후보로 수집하고, 기본 브랜치 포함 여부와 기여자를 확인한다.
- 작성·리뷰·공동 작업을 구분한다. PR 작성자라는 이유만으로 변경 전체를 개인 성과로 확정하지 않는다.
- 리뷰 기여는 실제 제안과 반영 근거가 있을 때 기록한다. 승인 버튼만 누른 활동은 우선순위를 낮춘다.
- 여러 계정·커밋 이메일의 동일인 여부는 사용자 확인 또는 검증된 연결로 판단한다.

## 3. 수집과 검사

입력 범위는 사용자가 선택한 저장소와 조회 기간이다. 저장소마다 공급자와 연결 방식을 지정한다. 공통 수집 대상은 커밋·작성자·변경 파일·diff·브랜치 관계다. PR·이슈·리뷰·논의는 공급자의 접근 가능한 기능으로 보강한다. PR이 없는 저장소에서도 커밋 기반으로 동작해야 한다. 상세 정책은 [다중 저장소 공급자 지원](repository-providers.md)을 따른다.

원본 전체를 즉시 LLM에 보내지 않는다. 메타데이터를 먼저 가져와 후보를 선별한 뒤 필요한 근거만 추가 수집한다.

검사 항목:

- 기여: 해당 사용자의 작성·수정·리뷰 근거가 있는가.
- 목적: 변경 목적과 해결하려는 문제가 드러나는가.
- 판단: 기술 선택과 제약이 기록되어 있는가.
- 검증: 테스트 결과·측정 기록·관측 가능한 기능 변화가 있는가.
- 완전성: API 제한, 누락된 patch, 접근 불가 자료가 있는가.
- 중복: 같은 문제를 다른 커밋이나 기간에서 중복 성과로 계산하는가.

포맷 변경·생성 코드·lockfile·단순 버전 갱신 등은 낮은 우선순위로 둔다. 보안 패치, 호환성 개선, 문서 기반 업무 개선처럼 의미 있는 결과는 사용자가 다시 포함할 수 있다. 필터링은 삭제가 아니라 가역적인 제외다.

## 4. 사실과 추정의 구분

문제·대안·구현·결과에 대한 개별 주장마다 상태를 둔다.

- `source_supported`: 원본 기록이 직접 뒷받침한다.
- `user_confirmed`: 사용자가 보충하거나 확인했다. 저장소 원본 근거와 구별해 보존한다.
- `inferred`: 정황상 추정이다. 확정 표현으로 내보내지 않는다.
- `missing`: 설명을 완성할 근거가 없다.

근거가 부족하면 질문을 만든다. 예: “락 대신 멱등성 키를 선택한 이유가 무엇인가요?”
질문에 답하지 않아도 다른 확실한 사실로 제한된 초안을 제공할 수 있다. 모든 빈칸을 LLM으로 채우지 않는다.

검증 규칙:

- 테스트 파일 추가와 테스트 실행 성공을 구분한다.
- CI 성공은 해당 실행과 SHA의 결과다. 운영 장애 감소를 증명하지 않는다.
- PR 병합과 배포를 구분한다. 배포 근거가 없으면 운영 적용을 주장하지 않는다.
- 코드 변경량과 업무 성과를 구분한다.
- 수치는 값·단위·전후 조건·출처를 함께 저장한다.
- LLM의 자신감 점수만으로 사실을 승인하지 않는다.
- 구조화 출력 형식이 맞아도 사실이 맞다는 뜻은 아니다.

## 5. 기간 규칙

기본 모드는 기준 시점에서 과거로 계산하는 rolling window다. 달력 기준 주간·월간 보고서는 추후 선택 옵션으로 둔다.

- 시간대 기본값: `Asia/Seoul`. 저장은 UTC로 하고 표시와 기간 계산에 시간대를 반영한다.
- 범위는 `[start_at, end_at)`로 고정한다. 조회 시 계산한 절대 시각을 저장한다.
- 1주일은 현지 달력 기준 7일, 1·3·6개월은 달력 월을 빼서 계산한다. 월말은 해당 월 마지막 유효 날짜로 맞춘다.
- 예: 종료가 2026-10-20 00:00 KST이면 1주일 시작은 10월 13일, 1개월 시작은 9월 20일이다.
- 1주일: 작업 진행, 판단 근거, 확인할 질문을 축적한다.
- 1개월: 완료된 문제 해결 사례와 본인 기여를 정리한다.
- 3개월·6개월: 같은 사례 중 대표 성과와 역량을 선별한다.

기간 선택은 이력의 완료 시점과 활동 시점을 구분한다. PR 기반 건의 기본 완료 근거는 `merged_at`이며 제품 성과 발생 시점과 동일시하지 않는다. 여러 PR이 연결된 건은 명시적인 마일스톤 또는 사용자 확인으로 완료를 판단한다. 직접 커밋은 기본 브랜치 반영 확인 시점과 관측 근거를 저장한다.

Git만 연결한 경우 author date·committer date·최초 수집 시각·기본 브랜치에서 처음 관측한 시각을 구분한다. 최초 과거 수집에서는 실제 push·merge·완료일을 알 수 없을 수 있다. 커밋 날짜는 활동일의 대체 기준으로 표시하고, 완료 근거가 없으면 완료일을 미확인으로 남긴다. PR이 없다는 이유로 해당 작업을 제외하지 않는다.

진행 중인 건은 해당 기간의 기여로 표시하고 완료 성과와 구분한다. 이전 기간에 시작했어도 현재 기간에 완료됐다면 완료 사례로 선택할 수 있다. 완료 후의 설명 보강·댓글 수정은 완료일을 바꾸지 않는다.

1개월·3개월·6개월 범위는 서로 겹칠 수 있다. 각 결과에 같은 사례가 등장할 수 있지만, 하나의 결과 안에서는 `work_item_id`로 중복을 제거한다. 주간 문장을 월간 문장으로 반복 요약하지 않고, 구조화된 근거를 직접 조회한다.

## 6. 출력과 사용자 검토

성과별로 제공할 항목:

- 한 문장의 이력서 초안.
- 문제, 제약, 비교 대안, 선택 이유, 구현, 결과와 검증.
- 본인 기여 유형과 기여 근거.
- 원본 링크와 해당 시점의 근거 스냅샷.
- 미확인 주장, 누락 근거, 보충 질문.
- 포함 기간과 완료·진행 상태.

예시 문장 — 형식을 설명하기 위한 가상 사례:

> 동시 요청 시 발생하던 중복 주문 문제를 멱등성 키 기반 처리로 개선하고, 동시성 테스트로 중복 생성 방지를 검증했다.

사용자가 수정한 문장과 승인한 사실은 버전으로 보존한다. 이후 자동 재생성이 덮어쓰지 않는다. 새로운 원본과 충돌하면 재검토 대상으로 표시한다.

## 7. MVP와 제외 범위

MVP는 1인 사용과 선택한 소수 저장소를 전제로 한다. 이후 서비스 확장이 가능하도록 소유자 경계를 둔다.

포함:

1. 선택한 저장소에서 기간별 기록 수집.
2. 규칙 기반 후보 선별과 명시적 연결 기반 묶기.
3. 후보별 구조화 분석과 근거 연결.
4. 사용자 보충·수정·승인.
5. 네 가지 기간의 한 문장 성과와 상세 근거를 Markdown으로 출력.
6. 호출 수·토큰·재사용률·누락 근거 기록.

후순위:

- 자동 지원, 이력서 외부 전송, 채용 사이트 연동.
- 전체 저장소의 정적 분석·실행·보안 감사.
- 커밋 수에 근거한 개발자 실력 점수.
- 외부 운영 지표 자동 수집, 다중 에이전트 토론.
- 전용 벡터 DB, 전체 코드 임베딩, 그래프 DB.

## 8. 성공 기준

- 최종 사실 주장에 원본 또는 사용자 확인 출처가 연결된다.
- 근거 없는 수치·트레이드오프·개인 기여의 확정 표현이 없다.
- 동일 입력·동일 설정으로 재요청하면 추가 LLM 호출이 없다.
- 기간만 바꾸어도 기존 작업 분석은 재사용한다.
- 중복 webhook과 재시도에서 성과 및 작업 레코드가 중복 생성되지 않는다.
- 비용 예산 초과와 수집 불완전성을 숨기지 않는다.
- 성능과 비용의 목표치는 실제 표본 평가 후 확정한다. 설계 단계에서 절감률을 보장하지 않는다.
